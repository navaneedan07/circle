# Circle

> **Your conversations are scattered. Circle brings the context together and lets you ask about the people who matter to you.**

Circle is a **private, local-first relationship intelligence application**. It unifies your
scattered personal data — contacts, chats, email, calendars, notes and voice recordings —
into one system where you can **select a person and ask natural-language questions** about
your relationship with them. Answers are generated by a **local open-weight model (Gemma via
Ollama)** and always come with **clickable sources** pointing back to the original records.

---

## 1. The problem

Context about the people in your life is scattered across WhatsApp, Telegram, email,
calendars, voice memos and your own notes. Remembering *where* you discussed something with
someone is exhausting. Circle remembers the context for you — on your own machine.

## 2. Features

- **Folder watcher** — drop exports into a watched folder; Circle detects, parses,
  de-duplicates and indexes them automatically (survives restarts). Watch **several**
  folders at once, including a Google Drive backup folder.
- **Read-only for your folders** — a folder you own (Drive, OneDrive, Downloads) is read
  in place: nothing is moved, renamed or deleted inside it.
- **People & relationship profiles** — automatic identity resolution across sources,
  explainable activity status ("Active — 12 interactions in the last 14 days"), topics,
  timelines, upcoming events.
- **Ask anything** — hybrid RAG (vector + keyword) over your data with source-cited answers.
- **Prepare me** — evidence-grounded meeting briefs.
- **Voice ingestion** — recordings dropped into `imports/voice/` are transcribed **locally**
  (Whisper) and become searchable memories.
- **Global search** across messages, emails, notes, calendar, voice transcripts, documents.
- **Real-time UI** — SSE updates while the watcher processes files.
- **Import jobs UI** — QUEUED → PROCESSING → COMPLETED/FAILED/QUARANTINED with error detail.
- **Offline-capable** — after models are installed, no internet is required.

## 3. Architecture

     Messages       Personal       Voice
     & Chats          Data        Recordings

        └──────────────┼──────────────┘

## 4. Privacy model

- **Local-first.** All processing runs on your machine. Personal data is never sent to
  external services.
- **No scraping.** Circle never scrapes websites, never automates logins, never asks for
  social-media passwords, and never bypasses platform APIs or privacy controls.
- **Exports only.** Social/messaging data comes exclusively from *your* official exports
  (WhatsApp/Telegram/Instagram/X), local files, official APIs (none configured by default),
  and data you create inside Circle.
- **Origin labels.** Every record is marked `api`, `imported`, or `local` so you always know
  where data came from.
- **Voice safety.** Circle never activates a microphone, never records calls, and only
  processes recordings *you* place in `imports/voice/`. Person associations for voice are
  **suggestions you confirm**.
- **Logs are content-free.** Log lines and Sentry events contain metadata only (source,
  operation, latency, counts, error type) — never message bodies.

## 5. Local AI

| Role | Provider | Default |
|---|---|---|
| Reasoning / answers | Ollama | `gemma3:4b` (configurable) |
| Embeddings | Ollama | `nomic-embed-text` (configurable) |
| Speech-to-text | faster-whisper (local) | `base` |
| Voice output (optional) | ElevenLabs | disabled unless you configure a key |

Both providers sit behind abstractions (`LLMProvider`, `EmbeddingProvider`,
`SpeechToTextProvider`) so models can be swapped without touching the app.

**Why Gemma?** Private reasoning: your relationship data is processed by a model running on
your own hardware. **Why SQLite?** The archive is one file, so there is no database service to
install or keep running, and backing up or deleting everything is one operation. MongoDB
remains supported for larger archives. **Why Sentry?** Observability for a multi-stage AI pipeline
without logging private content. **Why ElevenLabs (optional)?** Read answers aloud while
the knowledge pipeline stays local — only the final answer text is sent.

## 7. Folder watcher

`IMPORT_ROOT` **is** the folder you watch (default `backend/Circle-data`, set it in
first-run or via `.env`). Source subfolders live directly inside it, and the output
folders sit beside it:

```
C:\Circle\                              <- parent
├── imports\                            <- IMPORT_ROOT (watched, recursive)
│   ├── whatsapp\   telegram\   instagram\   x\   chats\
│   ├── voice\      email\      calendar\    contacts\
│   └── documents\  notes\
├── processed\                          # ingested files move here
├── failed\                             # unparseable files (+ job error shown in UI)
├── quarantine\                         # security-violating files
└── tmp\                                # scratch space for safe ZIP extraction
```

### Watch several folders at once

`IMPORT_ROOT` stays the main folder, and you can add as many extra watch folders as you
like (Settings → *Watch folders*, or `WATCH_ROOTS` in `.env`). Each folder is watched
recursively and source subfolders (`whatsapp/`, `instagram/`, …) are detected by name in
every one of them. Adding or removing a folder takes effect immediately, without a restart.

**Circle never moves files out of a folder you own.** Only Circle's own managed folder is
reorganized into `processed/` afterwards. That rule is the whole reason a Drive folder is
safe to point at: moving a backup inside a synced folder would delete it from your Drive
and re-upload the copy. Re-imports of the same file are suppressed by content checksum, so
leaving files in place costs nothing.

### Watching a Google Drive folder (or OneDrive, Dropbox, iCloud)

Circle does not sign in to Google, does not store Google credentials, and has no Drive API
integration. You sync the folder yourself with the vendor's own desktop client, and Circle
watches the local path that client provides.

1. Install **Google Drive for Desktop** from
   [google.com/drive/download](https://www.google.com/drive/download/) and sign in there.
2. In Drive, decide what Circle may read. A folder such as
   `G:\My Drive\Chat Backups\whatsapp\` is enough; nothing else is exposed.
3. In Circle: first-run asks for it, or Settings → *Watch folders* → paste the path
   (detected Drive locations are offered as one-click buttons). Or set it in `.env`:
   ```ini
   WATCH_ROOTS=G:\My Drive\Chat Backups
   ```
4. Keep the `.zip` exactly as WhatsApp or Instagram produced it. Subfolders named
   `whatsapp/` and `instagram/` route automatically; otherwise the filename decides.

Streaming mode caveats, handled for you: a Drive *placeholder* reports its full size from
remote metadata while having no local bytes, so a naive size-stability check would hash a
file that is still downloading. Circle detects the recall attributes
(`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` and friends) and downloads the file first
(`CLOUD_MATERIALIZE_TIMEOUT`, 600 s by default) before measuring or hashing it. Circle also
never creates subfolders inside your Drive folder: empty `whatsapp/`, `telegram/`, … stubs
would sync straight back to Google.

If you would rather not hold the backups on disk at all, use **mirror mode is not
required** — streaming mode works; the trade-off is that the first read of each file waits
for the download.

### What to download, and where to put it

You never need to extract anything by hand — **drop the archive (or folder) as it came
from the platform** into the matching subfolder:

| Platform | What to download | Drop into |
|---|---|---|
| WhatsApp | Chat → *More* → *Export chat* → **Include media** (the `.zip`) *or* Without media | `whatsapp/` |
| Telegram Desktop | *Settings → Advanced → Export Telegram data* → **JSON** (`result.json`) | `telegram/` |
| Instagram | *Accounts Center → Your information → Download your information* → **JSON** (not HTML) | `instagram/` |
| X / Twitter | *Settings → Your account → Download an archive* (`data/*.js` DM files) | `x/` |
| Voice memos | `.wav` `.mp3` `.m4a` `.ogg` `.webm` you recorded/exported | `voice/` |
| Email | `.eml` `.mbox` `.csv` `.json` | `email/` |
| Calendar | `.ics` `.csv` | `calendar/` |
| Contacts | `.csv` `.vcf` | `contacts/` |
| Documents | `.pdf` `.docx` `.txt` `.md` `.html` | `documents/` |
| Google Takeout | the outer `.zip` (nested archives are unpacked automatically) | any of the above |

**Putting it in the wrong place is not fatal.** Routing is decided by, in order:
(1) the subfolder, (2) the filename (`WhatsApp Chat with X.zip`), (3) the *content*
(a Telegram `result.json` dropped in `whatsapp/` is still parsed as Telegram), then
(4) the parser chain for the extension. `processed/`, `failed/` and `quarantine/` are
output folders — files placed there are ignored so the watcher never loops on its own moves.

### What happens to a `.zip`

1. Size/type validated, SHA-256 computed, duplicate check against already-processed files.
2. Safely extracted to `tmp/`: **zip-slip/path-traversal blocked**, absolute and drive
   paths rejected, entry-count and uncompressed-size caps enforced.
3. Each entry processed: supported formats parsed, **real media files (jpg/png/opus/mp4/…)
   copied into the local media store and linked to the messages that referenced them**,
   nested `.zip` recursed (up to 3 levels, e.g. Takeout).
4. Original archive is moved to `processed/`, temp extraction always deleted, and the job
   shows `imported` vs `skipped` counts in the Imports page.

### Media attachments (photos, voice notes, video, stickers, docs)

When a WhatsApp export contains media, Circle opens the files and ties them to the exact
message that referenced them — the `IMG-…jpg (file attached)` / `<attached: …>` line in
`_chat.txt` is matched to the real file inside `Media/`:

- The file is copied into a **content-addressed local media store**
  (`processed/media/<aa>/<bb>/<hash>-<name>`); identical files are stored once, and files
  never leave this machine.
- The message keeps the attachment and gains a `media_ids` link; photos, videos, stickers
  and documents render inline in the person timeline.
- **Voice notes** (`PTT-*.opus`, `AUD-*`) are transcribed **locally** with Whisper and the
  transcript is indexed as searchable evidence tied to the person (click a source to read
  it). Enable it by pulling a Whisper model — same local STT as `voice/` imports.
- **Photos can be captioned on demand** with the local multimodal model (Gemma vision);
  the caption becomes searchable evidence. This never sends the image anywhere.
- Order does not matter: media dropped **before** or **after** the chat file is linked to
  the message that named it, and a `<Media omitted>` export is stored as a placeholder
  with no file.

Media is served only by id from the store (`/api/media/{id}`); the API resolves the disk
path itself and checks it stays inside the media store, so a request can never read an
arbitrary file.

### Browser downloads are handled

`.crdownload`, `.part`, `.partial`, `.download`, `.tmp`, `~$`, `.#` and `.DS_Store` are
ignored, and zero-byte files are parked until content arrives — so a file still being
downloaded is never ingested, never counted as failed and never quarantined. When the
browser renames it to the final name, the normal ingest runs.

Pipeline: `detect → validate → SHA-256 → duplicate check → parse → normalize →
resolve identities → store (deterministic dedupe) → embeddings → relationship metrics →
notify UI → move to processed/`.

Windows-aware: waits for file size stability (partially copied files), retries locked files,
deduplicates bursty events, handles renames/deletes, and resumes interrupted jobs after a
restart. One broken file **never** stops the watcher.

## 8. RAG architecture

```
question → intent + person identification → metadata filters
        → vector retrieval (cosine over stored embeddings / Atlas $vectorSearch)
        → keyword retrieval (FTS5 full-text index)
        → reciprocal-rank fusion → context assembly ([S1]… evidence block)
        → local Gemma → citation validation → answer + sources
```

**Hallucination control:** citations are validated against the evidence actually supplied;
unknown ids are stripped; if no evidence exists the model is never called and Circle answers
*"I couldn't find enough evidence in your imported data."* Answers without valid citations
are treated as insufficient rather than presented as fact. Emotional/mental-health
inferences about people are never generated.

## 9. Setup

### As an app

Download `Circle.exe` from the download page, install
[Ollama](https://ollama.com/download), pull the two models, and run it. There is
nothing else to install: the archive, the interface and the local model all live
on your machine. See [BUILDING.md](BUILDING.md) to produce that file yourself.

### From source

Install **Ollama** and **Python 3.11+**, then:

```bash
ollama pull gemma3:4b          # ~5GB, one time
ollama pull nomic-embed-text   # ~300MB, one time
cd backend
./scripts/serve.sh             # macOS/Linux    (Windows: scripts\serve.bat)
```

Open `http://127.0.0.1:8000`. The first screen walks through choosing a folder
to watch and checking that everything is healthy.

`serve.sh` creates the virtualenv, installs dependencies, builds the interface
and starts the server. On first run it also generates an **access key** and
writes it to `backend/.env`; keep that file private. Once the server answers,
it opens `http://127.0.0.1:8000` in your browser. Set `CIRCLE_NO_BROWSER=1` to
skip that (useful on a headless machine or in a script). Both launchers work
from any directory and are safe to run again: the second run skips the steps
it has already done.

Before starting, the launcher runs a **first-run check** of the archive folder, Ollama,
both models and Node. If something is missing it prints the exact command to
fix it and stops, rather than starting an app where nothing works. Run it on
its own any time:

```bash
cd backend
.venv/Scripts/python scripts/doctor.py          # add --json to script it
```

Set `CIRCLE_SKIP_DOCTOR=1` to start without the check.

### Reaching Circle from another device (optional)

Not needed for normal use, and worth understanding before enabling it: a
tunnel address is **public**. Anyone who has it, and the access key, can read
your archive and permanently delete records.

Circle is loopback-only by default and refuses remote callers unless you opt
in. To open it from another machine on your own network, forward the port
yourself and set an access key:

```bash
# backend/.env
ACCESS_KEY=<a long random string>
ALLOW_REMOTE=true
CORS_ORIGINS=http://192.168.1.20:8000
```

Then visit `http://<this machine's LAN address>:8000` from the other device.
For anything beyond your own network, prefer not to: deploying the backend to a
cloud host would need a GPU for the model, local files for the watcher, and
would undo the privacy model this app is built on.

## 9a. Using Circle

Ask in plain language. Counts and rankings are answered from your database in
milliseconds, so they are exact; anything needing reading and phrasing goes to
the local model and can take a minute on a CPU.

| Question | How it is answered |
| --- | --- |
| who do I talk to the most | counted from your archive |
| who did I talk to in the last 7 days | counted |
| how many messages last week | counted |
| how many people have I talked to | counted |
| what are my top topics | counted |
| what did we discuss about the internship | local Gemma, with sources |

`Ctrl K` (or `/`) searches every message. On a person's page, search is scoped
to them.

## 12. Merging people who look like the same human

Importing chat exports can split one human into several records when the same
name arrives from different threads or platforms. Circle never merges on its own:
it queues the pair and you decide in **Settings > Possible matches**.

```bash
cd backend
.venv/Scripts/python scripts/find_duplicate_people.py --dry-run   # just show them
.venv/Scripts/python scripts/find_duplicate_people.py             # queue them
```

Names are compared after mojibake repair and with punctuation, emoji and
whitespace removed, so `Jineen` and `Jineen 🐾` are treated as one name. The
record kept is the one with the most recorded interactions. Accepting a
suggestion reassigns every message, memory, event, note, email and voice
recording onto the surviving person and records the old id in `merged_from`;
rejecting it leaves both people untouched. Re-run the script after a new import,
since more duplicates can appear.

## 13. Performance on CPU (measured, not guessed)

Local inference on a CPU has one dominant cost: **prompt processing**. Profiling
(`backend/scripts/profile_ask.py`, `backend/scripts/bench_ollama.py`) on an
i5-12450H (8C/12T, 16 GB, no discrete GPU) showed prompt evaluation ≈ 75 ms per
token, versus ~140 ms/token for generation — so **the size of the evidence block
matters more than anything else**.

Measured on the same machine, same question, back to back:

| Configuration | Prompt tokens | Prompt eval | Total answer |
|---|---|---|---|
| gemma3:4b, unbudgeted context (10 records × 900 chars), no keep-alive | 745 | 53.4 s | **64.2 s** |
| gemma3:4b + evidence budget + keep-alive + token caps *(new defaults)* | 426 | 30.6 s | **41.4 s** |
| gemma3:1b *(fast mode)* + new defaults | 426 | 8.1 s | **13.5 s** |

What changed, and why:

1. **Evidence budgeting** — the context block is capped by *total characters*
   (`RAG_TOTAL_EVIDENCE_CHARS`) as well as record count, and snippets are trimmed
   at word boundaries. ~35% faster end to end, and the answer stays focused.
2. **`keep_alive=30m`** — Ollama keeps models resident; without it every question
   paid a multi-second model reload (`load_ms` is now ~200 ms warm).
3. **`num_ctx=4096`** — a smaller KV cache directly reduces prompt-processing and
   memory pressure (`OLLAMA_NUM_CTX`).
4. **Token caps** — answers are limited to `LLM_MAX_ANSWER_TOKENS` (320) and briefs
   to `LLM_MAX_PREP_TOKENS` (600); each 100 generated tokens costs ~14 s here.
5. **Startup warm-up** — models are preloaded in the background, so the first
   question isn't the slowest one.
6. **Token streaming** — `/api/ask/stream` renders the answer as it is written.
   On gemma3:4b the first words appear at **21.9 s instead of 30.2 s** of blank
   waiting; on gemma3:1b the whole answer lands in ~13 s.
7. **Model choice is the biggest lever** — per-token cost scales with model size
   on this CPU (gemma3:1b measures ~19 ms/token prompt eval vs ~75 ms/token for
   gemma3:4b). Settings → *AI performance* switches models in one click and shows
   live tok/s, prompt-eval and advice.

Optional Ollama-side tuning (set before starting Ollama): `OLLAMA_FLASH_ATTENTION=1`,
`OLLAMA_KV_CACHE_TYPE=q8_0`. On this machine they made no measurable difference for
gemma3, and the numbers above are with them **on**. `RAG_MAX_EVIDENCE`,
`RAG_EVIDENCE_CHARS` and the token caps are all configurable if you prefer richer
context over speed (or vice versa).

## 14. Testing

```bash
cd backend
.venv/Scripts/python -m pytest tests/ -q                      # SQLite (default)
STORAGE_BACKEND=mongo .venv/Scripts/python -m pytest tests/ -q # MongoDB
MONGO_TESTS=1 .venv/Scripts/python -m pytest tests/test_storage.py -q
```

The suite runs against either storage engine (`STORAGE_BACKEND`), which is how a
storage port earns trust: the same assertions have to hold on both. With
`MONGO_TESTS=1` it additionally compares the two engines directly, so a
divergence shows up as a failure rather than as a wrong number nobody notices.

474 tests cover: all parsers (happy path **and** edge cases), ZIP security (zip-slip,
traversal, bombs), duplicate detection, identity resolution (no silent merges),
duplicate-person review, relationship metrics (explainable status), RAG citation
validation (fabricated citations rejected), deterministic counting intents
(counts come from the database, never from the model), topic-noise filtering
(including the guarantee that filler rules never drop a real subject),
paginated and sorted people queries, multi-folder watching, cloud-placeholder
materialization, the rule that a folder you own is never reorganized, the
ingestion pipeline (failures → `failed/`, one broken file never stops the rest)
and the REST API.

### What runs without the model

Countable questions are answered by SQL aggregations over the archive, not by Gemma. Asking a
4B model to count over 100k records produces a confident wrong number copied out
of whichever message it retrieved: "how many people have I talked to" once
answered *"109 people responded to a trip"*, a number that appeared inside a chat.

| Question | Intent | Source of truth |
| --- | --- | --- |
| who do I talk to the most | `top_people` | `interaction_totals` group-by |
| how many messages last week | `activity_count` | `activity_totals` group-by |
| how many people have I talked to | `people_count` | `distinct_people` |
| when did I last talk to X | `last_interaction` | indexed max on `occurred_at` |
| who did I talk to in the last 7 days | `recent_people` | `interaction_totals` + window |
| what are my top topics | `top_topics` | summed profile topics |

Each returns in milliseconds with a citation row, and never calls the model.
A count scoped to a subject ("how many messages did he say *about* the trip")
is deliberately **not** captured here, because no plain aggregate can answer it
and a wrong number is worse than a slow honest one.

| --- | --- |
| `Ctrl K` or `/` | Search every imported message (hybrid keyword + meaning) |
| `↑` `↓` then `Enter` | Move through results and open the person |
| `Esc` | Close search or an evidence dialog |
| `Tab` | Visible focus ring on every control; first stop is "Skip to content" |

On a person's page, search is scoped to that person's messages only. The
question box takes `Enter` to ask, and keeps what you have asked this session
so a follow-up can refer back to it.

## 15. Security

Input validation · file-size limits · SHA-256 integrity · ZIP-slip/path-traversal
protection · archive entry limits · filename sanitization (Windows reserved names,
traversal, control chars) · MIME/extension allow-lists · parameterized queries ·
secrets only via environment variables · **no passwords or platform credentials are ever
stored** · no sensitive content in logs or error tracking · binds to `127.0.0.1` by default.

## 16. Honest limitations

- No official WhatsApp/Instagram/X APIs exist for personal DMs → Circle uses **your
  exports** only. There are deliberately **no fake "Connect WhatsApp" buttons**.
- Cloud storage is a **folder**, not a connection: Circle watches a path that Google Drive
  for Desktop (or OneDrive, Dropbox, iCloud) already synced. There is no OAuth inside
  Circle and it holds no Google or Microsoft credentials.
- Watching a cloud folder in streaming mode means the first read of each file waits for
  that file to download. Circle waits and verifies it, but a 5 GB archive will take as
  long as your connection takes.
- Person identity resolution is deterministic-first; uncertain matches are *suggestions*
  you confirm — never automatic merges.
- Whisper transcribes *your* voice; it does not identify speakers by voice.
- Voice output (ElevenLabs) and Sentry are optional and disabled unless configured.
- Answer quality depends on your local model; a small model can be terse — but it cannot
  phone home with your data.
- The first whisper run downloads its model (one-time, needs internet); after that the
  whole app runs offline.

## 17. Future connectors

The connector architecture is extension-first: add a parser that normalizes into
`domain/models.py`, register a source folder, and the identity, RAG, relationship and UI
layers work unchanged — no AI/RAG code edits required.

**The core promise:** *Select a person → ask anything → Circle retrieves the evidence →
local Gemma answers with sources → new data arrives → profiles update automatically.*
